# 2D 渲染库调研（立绘角色）

**Status:** current
**Updated:** 2026-11-06

调研对象：在"角色渲染槽位"里承载 512×512 带 Alpha 立绘的 2D 渲染方案。
需要的不是通用绘图库，而是能把一张静态图**变形**、**叠滤镜**、**稳定 60 fps** 的
角色渲染层。

## 1. 需求清单

| 编号 | 能力 | 为什么需要 |
| --- | --- | --- |
| R1 | 带 Alpha 的纹理绘制与缩放 | 立绘是抠好的透明图 |
| R2 | 顶点/网格变形 | 呼吸、发丝与裙摆的摆动——整图变换做不出"活"的感觉 |
| R3 | 双图交叉淡化 | 四情绪切姿态，350 ms |
| R4 | 自定义着色或滤镜链 | 角色轮廓光、情绪色偏、柔光 |
| R5 | 高吞吐粒子 | 心情粒子与气泡特效，300~1000 个 |
| R6 | 正确的 Alpha 合成 | 边缘不能出现黑边或白边 |
| R7 | 低操作成本 | 一个角色，不是游戏引擎场景 |

R2 与 R6 是筛选线：前者排除所有"只做整图变换"的库，后者排除手写 WebGL 时最常见的坑。

## 2. 实测体积

方法可复现：各写一个只导入必要符号的入口，`esbuild --bundle --minify --format=esm`
打包后 `gzip -c | wc -c`。这是"这个库进包要付多少"的下限，不是官方宣传值。

| 入口 | gzip |
| --- | --- |
| 空入口（基线） | 0 KB |
| `two.js` | 49 KB |
| `konva` | 59 KB |
| `pixi.js`（`autoDetectRenderer` + `Container` + `MeshPlane` + `Texture`） | **151 KB** |
| `pixi.js`（常用入口，含 `Application`/`Assets`/`Filter`） | 172 KB |
| 自写 WebGL2（本项目代码，无依赖） | ≈ 4 KB |
| 原生 Canvas 2D（本项目代码，无依赖） | 0 KB |

`pixi.js` 的下限在 150 KB 左右——渲染器本体就是这么重，再省也省不下去。

## 3. 能力对比

| 库 | 渲染后端 | 网格变形 | 滤镜/发光 | React 集成 | 判断 |
| --- | --- | --- | --- | --- | --- |
| **原生 Canvas 2D** | Canvas 2D | 仅纵向切片（自写） | `ctx.filter` 模糊 + `lighter` 叠加 | 无需 | **入选：兜底与基线** |
| **PixiJS v8** | WebGL2 / WebGPU | `MeshPlane` 任意网格 + 自定义着色 | 滤镜链（Glow/Bloom） | `@pixi/react`（React 19） | **入选：主力** |
| 自写 WebGL2 | WebGL2 | 任意 | 自写多 pass | 无需 | 备选：省 150 KB，但要自己趟预乘 Alpha 与上下文丢失 |
| Konva | Canvas 2D | 无 | 少量内置滤镜 | `react-konva` | 不匹配：场景图面向图形与 UI，不是角色动画 |
| Two.js | Canvas/SVG/WebGL | 无 | 无 | — | 不匹配：体积小但在 R2/R4 上是空的 |
| Fabric.js | Canvas 2D | 无 | 无 | 非官方绑定 | 不匹配：编辑器那一侧的取向 |
| CanvasKit（Skia WASM） | WebGL | 强 | 强 | — | 过重：十兆级 WASM，对一个角色是杀鸡用牛刀 |

## 4. 逐项说明

**PixiJS v8（8.22.0）** — 唯一在 R2 + R4 + R5 同时达标的选择。
`MeshPlane` 提供规则网格，直接改顶点缓冲就能做双向变形（发丝、裙摆、呼吸），
也可以挂自定义 Filter 做轮廓光。v8 是一个包、一个入口，tree-shaking 有效，
`@pixi/react` 8.x 明确面向 React 19。代价是 151 KB 起步。

**原生 Canvas 2D** — 零依赖，`drawImage` 切横条做纵向偏移，能做出可信的呼吸与轻摆；
光晕用 `ctx.filter = 'blur()'` 或错位叠加实现。做不到 R2 的横向变形，
所以发丝不会摆。作为无 WebGL 环境的兜底，以及"零依赖基线"，它完全够用。

**自写 WebGL2** — 单纹理网格 + 一个着色器，约 200 行可以控制住，体积几乎为零。
但它要自己处理预乘 Alpha（否则立绘边缘发黑）、DPR、上下文丢失恢复。
把它作为 Pixi 之外的第三条路记录在案，不默认采用。

**Konva / Two.js / Fabric** — 三者都擅长"场景图 + 交互命中"，不擅长"把一张图揉变形"。
Konva 的滤镜是像素级而非顶点级；Fabric 面向编辑器的对象模型。
用它们承载角色，等于为了命中检测引入一整套用不上的抽象。

**CanvasKit** — Skia 编译成 WASM，质量上限最高，但十兆级体积与初始化时间与
"首屏 2.5 s 内可交互"直接冲突。

## 5. 建议

按里程碑分两步落地，先用最省的方式跑通，再上质感：

| 阶段 | 实现 | 目的 |
| --- | --- | --- |
| M1 | **原生 Canvas 2D** 适配器 | 零依赖跑通槽位协议、四情绪交叉淡化与呼吸；先把链路验证完 |
| M4 | **PixiJS v8** 适配器 | 网格变形（发丝/裙摆）+ 滤镜光晕；与 Canvas 2D 在调试面板里可切换对比 |

这样安排的理由：M1 要在半天内看到角色动起来，此时引入 151 KB 的渲染器会拖慢
"协议是否成立"的验证；等到 M4 打磨阶段，需求变成"能不能更好看"，
Pixi 的网格与滤镜才开始值这个体积。同一份槽位协议下，两者可共存、可对比，
调试面板的"渲染器"下拉也就成了一件有真实价值的功能，而不是摆设。

不选 Pixi 作为第一步，不是因为它不好，而是因为**槽位让顺序变得无关紧要**——
这正是这个架构要买的东西。

## 6. 风险

| 风险 | 对策 |
| --- | --- |
| Pixi 151 KB 拖慢首屏 | 适配器动态 import；Canvas 2D 先出画面，Pixi 在空闲时加载 |
| `pixi-filters` 最后发布于 2025-11 | 只用 `pixi.js` 内置 Filter 基类自写一个光晕，不引入 `pixi-filters` |
| 手写切片变形在移动端糊 | 切片数按显示高度自适应（24~40），`imageSmoothingQuality = 'high'` |
| Canvas 2D 在 Safari 的 `ctx.filter` 支持差异 | 检测能力，退化到"错位叠加 + 低透明度"的假光晕 |
| 两套适配器行为不一致 | 槽位协议里定义"最小可接受行为"，并对两个实现跑同一组状态序列的冒烟测试 |
